# Runtime feasibility plan — 29 October 2026

Recommendation: treat runtime feasibility as an independent, bounded experiment. The present Mac has an Apple M4 Max and 128 GiB unified RAM (read-only `sysctl`/`system_profiler` observation). DiffusionGemma is plausible on this machine; its guidance loop remains unproven. Support for small Macs is a separate product decision. No model was downloaded, installed, or benchmarked in this review, and no repository files were changed.

Updated first milestone: **a complete local Mac click-to-text demo**. Unblock it with frozen local generation plus exact text embedding and candidate selection; diffusion guidance proceeds as an optional backend experiment. Target the 128 GiB M4 Max first. Smaller Mac tiers and minimum-RAM promises come after measured compatibility.

Minimal first stack proposal: a single local Python worker, [`mlx-community/Qwen3-4B-4bit`](https://huggingface.co/mlx-community/Qwen3-4B-4bit) through MLX LM for candidate generation, and unquantized EmbeddingGemma through its standard SentenceTransformers/PyTorch CPU scoring pipeline. The named generator's publisher provides explicit MLX LM loading instructions; it is a concrete starting point, not a claim of best current quality. Keep the UI/runtime boundary plain JSON and pin exact revisions during implementation. This baseline needs no differentiable bridge. For the diffusion spike, use the concrete DiffusionGemma 4-bit mlx-vlm checkpoint and the same unquantized encoder; a PyTorch CPU input-gradient adapter is a correctness-first reference before any MLX encoder port. Transfer only sparse selected proposal values, avoid copying the full logits tensor between frameworks, and report transfer time. This is a proposed stack, not tested compatibility or an interactive-performance claim.

## Verified facts and their limits

- Google's [model card](https://ai.google.dev/gemma/docs/diffusiongemma/model_card) confirms discrete block diffusion, causal prompt encoding/cache, bidirectional canvas decoding, 25.2B total / 3.8B active parameters, 256-token canvases, and 8 active of 128 experts plus a shared expert. Active parameters describe computation; they do not shrink the resident checkpoint to 3.8B parameters.
- Arithmetic, not a runtime measurement: 25.2B weights require 50.4 GB at 16 bits, 25.2 GB at 8 bits, or 12.6 GB / 11.7 GiB at nominal 4 bits. This excludes scales, zero points, higher precision tensors, activations, caches, encoder, and OS. A full 256 × 262,144 vocabulary float32 logits array is about 256 MiB before gradients and extra copies. Sparse/top-k bridges matter even when model weights fit.
- A [community MLX checkpoint](https://huggingface.co/mlx-community/diffusiongemma-26B-A4B-it-4bit) exists. Its [actual configuration](https://huggingface.co/mlx-community/diffusiongemma-26B-A4B-it-4bit/raw/main/config.json) uses group-64 affine 4-bit with explicit 8-bit exceptions, including embeddings, attention projections, routers, and some dense layers. Therefore “4-bit” is not a uniform 12.6 GB footprint or proof of quality preservation.
- The concrete Apple path is **mlx-vlm**, with [DiffusionGemma model code](https://github.com/Blaizzy/mlx-vlm/blob/main/mlx_vlm/models/diffusion_gemma/diffusion_gemma.py) and an explicit [diffusion generation loop](https://github.com/Blaizzy/mlx-vlm/blob/main/mlx_vlm/generate/diffusion.py). The inspected loop forms decoder logits, applies temperature, then samples and accepts tokens. Its public kwargs wrapper explicitly rejects `logits_processors`; ordinary generation callbacks do not establish an editable pre-sampler hook. A small maintained adapter around this loop is likely required. Pin an exact revision before implementing: `main` is mutable.
- Hugging Face's [Diffusers documentation](https://github.com/huggingface/diffusers/blob/main/docs/source/en/api/pipelines/diffusion_gemma.md) exposes interchangeable schedulers. In the inspected [pipeline implementation](https://github.com/huggingface/diffusers/blob/main/src/diffusers/pipelines/diffusion_gemma/pipeline_diffusion_gemma.py), the step-end callback occurs **after** `scheduler.step`, and its returned `canvas` is consumed while returned logits are not. It is not a same-step logit guidance seam. A scheduler wrapper can intercept `model_output` before sampling, but must preserve sampler state, self-conditioning, stopping, and corrector behavior. The pipeline uses `torch.no_grad`; encoder input differentiation would need an explicit grad-enabled region with detached generator proposals. CUDA compilation examples are not evidence of Apple MPS compatibility.
- [MLX `grad`](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.grad.html) supports derivatives with respect to selected array arguments. This establishes framework capability, **not** compatibility of an arbitrary sentence encoder, quantized operation, compiled sampler, or tokenizer bridge. A frozen encoder still needs a derivative graph for its floating-point inputs; token IDs and decode/re-tokenize operations are not differentiable.
- [EmbeddingGemma](https://huggingface.co/google/embeddinggemma-300m) is a 300M encoder with 768-dimensional output and 2,048-token input limit. [Transformers Gemma3 text code](https://github.com/huggingface/transformers/blob/main/src/transformers/models/gemma3/modeling_gemma3.py) exposes `inputs_embeds`; this is a candidate route, not a validated complete sentence-embedding adapter. Pooling, prompts, normalization, embedding scaling, masking, and dense heads must match the ordinary scoring pipeline exactly. Shared model branding or vocabulary size does not prove token-ID equivalence.

## Orthogonal workflow and first deliverable (proposal)

Keep runtime work independent of corpus selection, projection fitting, UI, and guidance-objective research. Give it fixed synthetic requests and real short prompts. It should return a **capability report and a reproducible one-command smoke test**, before committing architecture or a model-specific application server.

The smallest useful gate is:

1. Pin model/checkpoint revision, tokenizer hash, mlx/mlx-vlm versions, OS/chip/RAM; load and produce one default 256-token canvas. Capture cold load, warm prefill, time to first committed block, total wall time, denoise passes, peak memory, swap/memory pressure, and decoded text. Synchronize device evaluation around timing. Do not label partial denoising drafts as committed output.
2. Capture one proposal immediately before token acceptance; with a fixed seed, show a controlled logit perturbation changes the sampler input and resulting decisions. Show identity guidance leaves the adapter's result unchanged. Verify the same modified logits feed acceptance, entropy/stopping and self-conditioning consistently.
3. For one frozen embedding encoder, show normal text scoring equals the adapter's hard-token embedding path within declared tolerance. On a very short soft input, verify finite, nonzero input gradients and a directional finite-difference check, while all parameter values remain unchanged. Report tokenizer-overlap coverage and bridge memory. Hard decoded text must be scored through normal re-tokenization.
4. Run one combined encoder-loss update on detached proposal logits and finish generation; report soft loss and actual decoded-text error separately. This proves plumbing only. It does not establish steering effectiveness, quality, or interactive latency.

Expected artifacts: `capabilities.json`, pinned environment/model manifest, one small CLI, `smoke-result.json`, a per-step trace, and a short pass/fail report. Runtime gate passes only when loading, pre-commit interception, encoder derivatives, and combined execution are demonstrated. Select latency/memory acceptance thresholds with Emre rather than inventing a universal requirement; use a hard experiment timeout and memory ceiling once agreed. Broader quality comparisons belong to the subsequent research gate.

For the chosen demo milestone, its baseline gate is smaller: click → target → local candidate text → ordinary embedding → measured plotted location, with cancellation and clear remaining error. The diffusion capability remains disabled unless its extra checks pass. Before describing diffusion as useful steering, additionally require a reproducible real-text fixture with measured **hard decoded-text improvement** over an unguided run under the same wall-clock budget, then evaluate a broader target/seed set. A lower soft loss alone does not pass that claim.

## Fallbacks and stable seams (proposal)

If DiffusionGemma's loop is too costly or brittle, test [Dream 7B](https://github.com/DreamLM/Dream), with [MacPaw's Fast-dLLM-mlx](https://github.com/MacPaw/Fast-dLLM-mlx) as a concrete Apple implementation candidate. That repository documents Dream inference and a separate DiffusionGemma path; its published speedups are not measurements on this machine or of gradient guidance. Start with ordinary sampling before cache/compile optimizations. DiffuCoder is a useful engineering smoke-test model but its code specialization makes it a poor default for general prose.

If no local diffusion stack passes the gate, ship the useful research baseline: retrieve nearby real texts, generate several candidates with a supported local autoregressive model, embed/re-tokenize them normally, and select or iteratively revise by measured map error. This preserves arbitrary black-box encoders and supplies an equal-wall-clock comparison; it does not claim diffusion guidance. A remote GPU diffusion worker can remain an optional later backend.

Stable boundaries should distinguish capabilities:

- `TextScorer.encode(texts) -> embeddings` and immutable encoder/pooling/normalization identity.
- Optional `DifferentiableEncoder.loss_and_input_grad(soft_inputs, target)` plus a separately identified tokenizer bridge and coverage report.
- `GeneratorBackend.generate(request, optional_guidance) -> candidates + trace`, advertising `supports_precommit_logits`, runtime/device/dtype/quantization and cancellation support.
- Within a backend, `propose(canvas, context, state) -> detached_logits`, `guide(logits, step_context) -> logits`, then `commit(logits, sampler_state)`. Keep framework tensors inside that worker; UI and experiment records exchange plain text, IDs, coordinates, and scalar metrics, not huge logits over RPC.

Use an eager, correctness-first path for guidance. Compilation, quantization changes, caching and alternate samplers require equivalence checks because they may move the interception point, change gradients, or invalidate state. A PyTorch encoder beside an MLX generator is possible but cross-framework transfer and derivative boundaries must be measured; prefer a single stack when a correct encoder adapter exists. Do not make an inference-only server API the internal abstraction for a sampler-editing research system.
